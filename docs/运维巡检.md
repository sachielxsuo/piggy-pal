# 运维巡检与告警

> 本文里的 `203.0.113.10` / `piggy.example.com` 都是**占位符**（真实地址不入库），
> 换成本机 `deploy.env` 里的 `PIGGYPAL_SERVER` / `PIGGYPAL_DOMAIN` 后再执行。

> 目标：不是「服务进程活着」，而是「孩子点开就能用」。
> `/healthz` 只返回固定 `ok`，抓不到「服务活着但功能坏了」——2026-10-27 佩奇静音
> （TTS 资源包额度用尽）就是这种，全程 `healthz` 都是 200。

## 三道防线

| 层次 | 手段 | 频率 | 能发现 |
|---|---|---|---|
| 外部探活 | UptimeRobot 盯 `https://piggy.example.com/healthz` | 5 分钟 | 整机挂、端口不通、证书过期、部署后起不来、返回内容异常 |
| 功能巡检 | `piggy-pal-watchdog`（本机 systemd timer） | 10 分钟 | TTS 额度用尽 / 已切备用音色、服务端 ERROR、当天备份缺失、磁盘满 |
| 每日自检（可选） | 主音色合成 2 个字符 | 每天 | 没人使用时也能提前发现额度问题 |
| 异地备份 | 群晖 NAS 每天 04:00 主动拉取到 `<NAS 备份根>/piggy-pal` | 每天 | VPS 整机丢失 / 磁盘坏 / 误删时，仍有 180 天历史 |

> 两道防线互补：**整站挂了，本机 watchdog 也一起挂，只有外部探活能发现**；
> 反过来，进程活着但功能坏了，只有 watchdog 能发现。两个都要有。

## 外部探活（UptimeRobot，免费）

### 配置

新建 HTTPS 监控，字段如下：

| 字段 | 值 |
|---|---|
| Monitor Type | HTTPS |
| Friendly Name | `PiggyPal 服务` |
| URL | `https://piggy.example.com/healthz` |
| Monitoring Interval | 5 minutes（免费版固定） |
| Monitor Timeout | 30 seconds |
| Advanced → Keyword Type | `exists` |
| Advanced → Keyword | `"status":"ok"` |

Keyword 检查是必须的：只看 HTTP 200 的话，Caddy 返回一个空页面或错误页也会被判成正常。
`/healthz` 实际返回 `{"service":"piggy-pal","status":"ok"}`，所以关键词用 `"status":"ok"`。

告警渠道：**Email**（免费，手机邮箱 App 推送和微信一样即时）。短信/电话是付费功能，家庭项目不需要。

> ⚠️ **只监控 `/healthz`**。服务端除 `/healthz` 外所有接口都要求 `X-API-Token`
> （`/app/latest.json` 和 APK 下载也一样），拿它们做外部探活会一直 401 误报。

### 验证

1. 监控详情 → **Send test notification**，确认收到邮件
2. 想验证真的会报：把 URL 临时改成 `https://piggy.example.com/healthz-typo`，
   5–6 分钟后应收到 down，改回后应收到 up

### 免费版额度

50 个监控、5 分钟间隔、无信用卡。我们只用 1 个，288 次请求/天，无任何成本。


## 功能巡检检查项

`/opt/piggy-pal/piggy-pal-watchdog`，由 `piggy-pal-watchdog.timer` 每 10 分钟拉起：

| 检查 | 判据 | 告警标题 |
|---|---|---|
| 本机探活 | `curl http://127.0.0.1:18080/healthz` 失败 | 服务探活失败 |
| TTS 额度 | 最近 15 分钟日志含 `额度已用尽` / `改用备用音色` / `PkgExhausted` | TTS 额度异常，已切备用音色 |
| 其它错误 | 最近 15 分钟日志含 `level=ERROR`（排除额度相关，避免重复） | 服务端报错 |
| 每日备份 | 04:00 之后 `data/backups/app-YYYYMMDD-*.db.gz` 不存在 | 今天的数据库备份没生成 |
| 磁盘 | 根分区使用率 ≥ 85% | 磁盘快满了 |
| NAS 异地备份 | 配了 NAS 后，48 小时内没有任何一次拉取 | NAS 备份已 N 小时没来拉取 |

**去重**：同一个问题 6 小时内只推一次（`data/watchdog/last-<key>` 记时间戳），避免每 10 分钟刷屏。
**留档**：所有告警无条件追加到 `data/watchdog/alerts.log`，即使没配 webhook 也能事后回看。

## 发布窗口（2026-10-29 起）

2026-10-28 20:30 有一次「服务探活失败」误报，原因是部署脚本为了 `cp` 数据库先停了服务，
整个停服窗口被拉到 1 分多钟，正好撞上巡检。现在改成三件事：

### 1. 数据库在线备份，部署不再停服拷库

部署脚本用 `sqlite3 .backup` 热备（和每日备份同一套机制），不再 `systemctl stop` 之后 `cp`。
停服只发生在「换二进制」的那一下。

### 2. 维护标记：巡检整轮跳过

部署脚本在停服前 `touch data/watchdog/maintenance`，退出时（含失败）自动删除。
watchdog 看到标记直接 `exit 0`，不探活、不扫日志、不推告警。

标记超过 2 小时还没删，视为部署脚本异常退出（或人为误操作），watchdog 自动忽略并恢复巡检，
不会因为一个残留文件把告警永久静音。

### 3. 两个探针，语义分开

| 端点 | 语义 | 排空期间 | 谁在用 |
|---|---|---|---|
| `/healthz` | liveness：进程还活着 | **200** | UptimeRobot、watchdog |
| `/readyz` | readiness：能接新活 + 数据库可读 | **503** | 部署脚本、以后的切流 |

排空期间 `/healthz` 必须保持 200。否则一次发布的告警窗口会从几秒变成整个排空时长
（最长 130 秒），反而更容易撞上巡检。

### 4. 优雅退出

进程收到 SIGTERM 后：`readyz` 立刻 503 → 新请求由排空闸门直接返回 503
（保留监听端口，客户端拿到的是明确错误，不是 connection refused）→ 等在途请求跑完
（最多 130 秒）→ 关闭监听并退出。systemd `TimeoutStopSec=150` 比它长，不会被 SIGKILL 截断。

实际中断时间：

- 空载发布：约 1–2 秒（老进程退出 → 新进程 bind）
- 正在对话时发布：会等这条请求结束（典型 5–15 秒，最长 130 秒）再退出，**不丢消息、不断流**
- 部署后 30 秒内 `/readyz` 不就绪 → 自动回滚到 `.prev` 二进制和配置

### 5. 发布后确认

```sh
curl -s https://piggy.example.com/healthz   # {"service":"piggy-pal","status":"ok"}
ssh root@203.0.113.10 'curl -s http://127.0.0.1:18080/readyz'
ssh root@203.0.113.10 'ls -la /opt/piggy-pal/data/watchdog/maintenance'  # 应不存在
```

### 已知边界

- 单实例顺序替换，做不到严格 0 中断；要 0 中断需要双实例 + Caddy 切流（蓝绿），
  前提是 SQLite 已开 WAL（现在是 `WAL + busy_timeout=5000`）且迁移只增不改。
- 改列 / 删列 / 改语义的迁移无法新旧共存，只能停机发布。加字段可以无缝。

### TTS 是不是撞了单次长度上限

腾讯云基础语音合成单次上限：**中文 150 个汉字 / 英文 500 个字母**（全角标点算汉字，半角标点算字母），
超了返回 `UnsupportedOperation.TextTooLong`，那一段就没有声音（只降级成文字）。

```sh
# 1. 有没有撞上（新旧版本都能用：错误码会带在日志里）
grep -c "TextTooLong" /var/log/piggy-pal/server.log

# 2. 新版本（2026-10-29 之后）有独立一条，带用量和内容开头，方便判断是哪条内容
grep "TTS 文本超出长度限制" /var/log/piggy-pal/server.log | tail -20

# 3. 接近上限的预警（用量 >= 80% 时打 WARN，还没失败）
grep -c "TTS 文本接近单次长度上限" /var/log/piggy-pal/server.log

# 4. 看最近请求的用量分布（cjk=汉字数，latin=字母数）
grep "TTS 请求开始" /var/log/piggy-pal/server.log | sed -E 's/.*cjk=([0-9]+) latin=([0-9]+).*/cjk=\1 latin=\2/' | tail -20
```

巡检已经接上了这一项：窗口（15 分钟）内出现超长会推一条 **「TTS 文本超出长度限制（该段静音）」**
（告警键 `tts_too_long`，默认 6 小时去重），正常时打印 `· TTS 长度正常`。
它不算服务故障，所以从原来的「服务端报错」里摘出来了，不会让人误以为进程挂了。

判断口径：

- `TextTooLong` 长期为 0、也没有预警 → 不用管
- 出现预警但没失败 → 说明某条内容在变长（多半是睡前故事），先看 `text_head` 是故事还是聊天
- 真出现 `TextTooLong` → 那一段是静音的，需要给 TTS 加「按长度再切一刀」（`splitForTTS`），再逐段拼接
- 先看 `total_hits` 和 `text_head`：同一个内容反复超长＝那条内容的生成 prompt 要收紧；偶发一次可以忽略

> 只在**缓存未命中**时才会真的请求腾讯云，所以日志里的用量是真实发出去的请求；
> 命中的请求打的是 `TTS 命中缓存`，没有 cjk/latin 字段。

### 孩子一句话说多长（ASR 60 秒 / 3MB 上限）

```sh
# 真实识别时长（毫秒，腾讯云返回的）和识别耗时
grep "ASR 请求完成" /var/log/piggy-pal/server.log | sed -E 's/.*audio_ms=([0-9]+).*/\1/' | sort -n | tail -5
```

客户端录音上限 30 秒（16k 单声道 WAV ≈ 0.96MB / base64 后 1.28MB），离 60 秒 / 3MB 还有一半余量。
如果 `audio_ms` 经常顶到 28000–30000，说明孩子确实说不够，再考虑放开上限（要同时换 m4a/mp3 编码控体积）。

## 异地备份（群晖 NAS 主动拉取）

> 这里只备份**数据库**。密钥（`.env` / keystore / 部署配置）走
> `scripts/backup-secrets.sh` 打成一个 `tar.gz` 包，放到 `<NAS 备份根>/secrets/`，
> 和这个目录平级、互不相干。见 [密钥与恢复](密钥与恢复.md)。

### 为什么让 NAS 来拉，而不是 VPS 推

VPS 有公网 IP，NAS 在家、在 NAT 后面。要让 VPS 推过去，就得给 NAS 做 DDNS + 端口映射，把 SSH 暴露到公网——这是家庭网络最常见的入口。反过来让 NAS 出站拉取：

- VPS 不用开任何新入站端口，防火墙不动
- NAS 不暴露到公网，攻击面为零
- 只认公钥，密码登录已全局关闭

```
VPS 203.0.113.10                    家里 NAS（DSM）
/opt/piggy-pal/data/backups/  ←──  每天 04:00 主动 rsync 拉取
       （14 天轮转）                 <NAS 备份根>/piggy-pal/（180 天）
```

### VPS 侧（已配好，平时不用动）

| 项 | 内容 |
|---|---|
| 专用账号 | `backup`，无密码、只能公钥登录 |
| 命令限制 | `command="/usr/local/bin/rrsync-heartbeat -ro /opt/piggy-pal/data/backups"`，只读、不能 cd 出去、不能开 shell |
| SSH 限制 | `no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-user-rc` |
| 备份文件权限 | umask 027 → `640`，`backup` 靠 `piggy-pal` 组读 |
| 心跳 | 每次连接写 `/var/lib/piggy-pal-nas/last-pull`，超过 48 小时没更新就告警 |
| 启用标记 | `/opt/piggy-pal/.nas-backup-enabled` 存在才检查心跳 |

已验证（2026-10-28）：GNU rsync 3.2.7 真实拉取成功、gzip 完整、二次拉取无重复传输；
`cat /etc/passwd`、`/../../etc/`、写入 `/pwn.txt`、`id` 全部被拒绝。

### NAS 侧步骤（已完成 2026-10-28）

> 远程操作时**不用开 SSH**：DSM 的「任务计划」能以 root 身份跑脚本，
> 生成密钥 → 把公钥写进共享文件夹 → 用 File Station 取出即可。
> 这条路走的是 DSM 网页（QuickConnect 也能用），不需要内网、不需要端口转发。

1. DSM → 控制面板 → 终端机和 SNMP → 勾选「启动 SSH 功能」（**本方案不需要**，仅作备选）
2. 在 Mac 终端登录 NAS，切到 root：

```bash
ssh 你的DSM账号@192.168.1.x
sudo -i
```

3. 生成专用密钥（不设密码短语，因为它要无人值守跑）：

```sh
mkdir -p <NAS 备份根>/piggy-pal <NAS 备份根>/.ssh
chmod 700 <NAS 备份根>/.ssh
ssh-keygen -t ed25519 -N "" -C "piggypal-nas" -f <NAS 备份根>/.ssh/piggy_backup
cat <NAS 备份根>/.ssh/piggy_backup.pub
```

4. 把最后输出的那行 `ssh-ed25519 ...` 发给维护者，装到 VPS 的
   `/home/backup/.ssh/authorized_keys`（公钥可以公开，私钥永远不要发）

### DSM 任务计划

控制面板 → 任务计划 → 新增 → 计划的任务 → 用户定义的脚本：

- 用户账号：`root`
- 计划：每天 `04:00`
- 脚本：

```sh
#!/bin/sh
# PiggyPal 异地备份：从 VPS 拉取数据库备份（只读，VPS 侧用 rrsync 锁死）
# BASE 改成 NAS 上的共享文件夹路径（群晖默认在 /volume1 下）
BASE=<NAS 备份根>
VPS=<服务器IP或域名>
KEY=$BASE/.ssh/piggy_backup
DEST=$BASE/piggy-pal
WEBHOOK_FILE=$BASE/.ssh/wecom_webhook
LOG=$DEST/rsync.log
RSYNC=$(command -v rsync || echo /usr/bin/rsync)

mkdir -p "$DEST"
ok=1

"$RSYNC" -az --partial --timeout=180 \
  -e "ssh -i $KEY -o BatchMode=yes -o ConnectTimeout=15 -o StrictHostKeyChecking=accept-new" \
  "backup@$VPS:/" "$DEST/" || ok=0

# 校验最新一份能正常解压，防止半截文件被当成好备份
newest=$(ls -1t "$DEST"/app-*.db.gz 2>/dev/null | head -1)
if [ -n "$newest" ]; then
  gunzip -t "$newest" || ok=0
fi

if [ "$ok" = 1 ]; then
  echo "$(date '+%F %T') ok ${newest:-none}" >> "$LOG"
else
  msg="PiggyPal NAS 备份失败 $(date '+%F %T')"
  echo "$msg" >> "$LOG"
  if [ -r "$WEBHOOK_FILE" ]; then
    . "$WEBHOOK_FILE"
    curl -s --max-time 8 -H 'Content-Type: application/json' \
      -d "{\"msgtype\":\"text\",\"text\":{\"content\":\"$msg\"}}" "$WECOM_WEBHOOK" >/dev/null 2>&1
  fi
fi

# NAS 侧保留 180 天（VPS 只有 14 天）
find "$DEST" -type f -name 'app-*.db.gz' -mtime +180 -delete

# 日志只留最近 500 行
tail -n 500 "$LOG" > "$LOG.tmp" && mv "$LOG.tmp" "$LOG"

[ "$ok" = 1 ] || exit 1
```

**不要加 `--delete`**：VPS 只保留 14 天，NAS 要留 180 天。加了 `--delete` 会把 NAS
上的历史一起删掉，异地备份就退化成“和线上一样只有两周”。

失败通知：把 webhook 单独放一个文件，脚本里 source 它，避免把 key 写进任务计划：

```sh
printf 'WECOM_WEBHOOK=https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=你的key\n' \
  > <NAS 备份根>/.ssh/wecom_webhook
chmod 600 <NAS 备份根>/.ssh/wecom_webhook
```

### 验证

```sh

ls -lh <NAS 备份根>/piggy-pal/
```

### 恢复演练

```sh
# 在 NAS 上取最新备份，解出来验一遍
gunzip -c "$(ls -1t <NAS 备份根>/piggy-pal/app-*.db.gz | head -1)" > /tmp/restore.db
sqlite3 /tmp/restore.db 'PRAGMA integrity_check;'
sqlite3 /tmp/restore.db 'select count(*) from chat_message;'
```

真要恢复时：停服 → 把解出来的库覆盖 `/opt/piggy-pal/data/app.db` →
`chown piggy-pal:piggy-pal` → 起服 → 看一眼 `/healthz` 和最近聊天记录。
恢复前先把当前库改名留底，别直接覆盖。

## 已知缺口（按优先级）

1. **没有每日合成自检**：低峰时段（比如深夜）没人用，额度问题要等第一个用户开口才暴露。加一个每天 12:00 用主音色合成 2 字符的检查即可，需要服务端加一个绕过缓存的内部接口。
2. **部署无二进制回滚**：线上异常要重新 `git checkout` + build（约 2 分钟）。可在部署时保留 `piggy-pal-server.prev`。
3. `server.log` 权限 644、客户端上传日志保留 8 周，日志里有宝宝的对话文本；在意隐私可收紧到 640 / 2 周。
4. NAS 恢复只演练过“解压 + integrity_check”，没做过整机替换演练；真出事按上面「恢复演练」走，先备份当前库再覆盖。
