# 密钥与恢复

> 这个项目有几样东西**丢了就真出事**，也有几样看着吓人其实随时能重建。
> 先分清哪些是哪种，再谈放哪儿。

## 一句话

**只有 keystore 不可替代。** 其余（CAM 密钥、DeepSeek Key、服务器地址）都能在控制台重新签发或查到，只是麻烦程度不同。

## 1. 资产清单

| 文件 | 里面是什么 | 丢了会怎样 | 能重建吗 | 现在有几份 |
|---|---|---|---|---|
| `~/keys/*.keystore` | Android 签名私钥 | 已安装设备**无法覆盖升级**，只能卸载重装 | ❌ **不能** | 本机 + 服务器 `/root/backups/keys/` + NAS 备份包 |
| `server/.env` | CAM 密钥、DeepSeek Key、`API_TOKEN` | 服务起不来 | ✅ 密钥可重签；**`API_TOKEN` 改了要重发 APK** | 本机 + 服务器 `/opt/piggy-pal/.env` + NAS 备份包 |
| `deploy.env` | 服务器 IP、域名 | 不知道连哪台机器 | ✅ `dig 你的域名` 就有 IP，腾讯云控制台也能查 | 本机 + NAS 备份包 |
| `client/android/key.properties` | 签名别名与口令 | 打不出包 | ✅ 口令就是 keystore 的口令，重新填一次 | 本机 + NAS 备份包 |
| `/opt/piggy-pal/alert.env` | 企业微信 webhook | 收不到告警 | ✅ 群里重新建一个机器人 | 只有服务器 |
| `data/app.db` | 全部业务数据 | 孩子学习记录丢失 | ❌ | 服务器 + NAS 每日（保留 180 天） |

> `API_TOKEN` 那个坑重复三次也不过分：**它被编译进 APK**。改了它，所有设备都要重新打包升级，否则全 401。

## 2. 放在哪儿

三层，各管一件事：

| 层 | 放什么 | 为什么 |
|---|---|---|
| **热副本**（服务器） | `.env`、keystore（`/root/backups/keys/`） | 服务在跑就得有；也是换电脑时最容易拿回来的地方 |
| **主备份**（NAS） | `scripts/backup-secrets.sh` 打出的 `tar.gz` | 一份文件保住全部；NAS 已有异地备份链路，不用再买服务 |
| **账号**（密码管理器） | 腾讯云 / DNS / GitHub 的密码、MFA 恢复码 | 真正会「一锅端」的是账号，不是文件 |
| **纸质**（可选但推荐） | 包放哪儿、keystore 指纹 | 唯一不会被「忘记密码 / 换手机没迁移 / 云盘封号」影响的形式 |

> ⚠️ 备份包是**明文**（`tar.gz`，没有口令）。安全边界只有一条：
> **它只放在你自己家里、只有你能登录的地方**。NAS 的 `secrets` 目录权限 700，
> 不进 git、不进 iCloud / 坚果云 / 微云这类同步盘，也不发微信传文件。
> 需要外发（比如传给另一台机器）时，自己另外用 `openssl` / `age` 加一层再发。

### NAS 放哪里

```
<NAS 备份根>/secrets/           ← 备份包放这里（700，只有管理员可读，明文）
<NAS 备份根>/piggy-pal/         ← 数据库备份（rrsync 每天拉取，别混）
```

**不要**把密钥包放进 VPS 的 `data/backups/`。那个目录通过 `rrsync` 对 NAS 只读开放，是给数据库用的，两者的生命周期和权限要求完全不同。

也不要把这个 `secrets` 文件夹通过 QuickConnect 或公网分享出去——NAS 之所以安全，就是因为它只在局域网里。

## 3. 怎么做备份

```sh
./scripts/backup-secrets.sh                 # 输出到 ~/piggypal-secrets
./scripts/backup-secrets.sh --out ~/Desktop # 指定目录
```

脚本会：

1. 收集 `server/.env`、`deploy.env`、`key.properties`、keystore（路径从 `key.properties` 的 `storeFile` 读，不写死任何本机路径）
2. 生成 `MANIFEST.txt`：文件清单、大小、SHA-256、keystore 指纹
3. 直接打成一个 `piggypal-secrets-YYYYmmdd-HHMMSS.tar.gz`（不加密、不设口令）
4. 打印包的大小和 SHA-256，提示下一步

没有交互、没有口令，跑一次就完事。打包完成后拷到 NAS：

```sh
scp ~/piggypal-secrets/*.tar.gz <NAS账号>@<NAS地址>:<NAS 备份根>/secrets/
```

直接拖进挂载的共享文件夹也行。**放之前确认那个目录只有你能读。**

**建议节奏**：密钥有变动就备份一次，没变动至少每季度跑一次（顺便演练恢复）。

## 4. 恢复演练（新电脑从零开始）

每季度做一遍，不做演练的备份等于没有备份。

```sh
# 1. 装工具：Go >= 1.22、Flutter、Android SDK、rsync
# 2. 拿代码
git clone <仓库地址> && cd piggy-pal

# 3. 从 NAS 取回最新的备份包
scp <NAS账号>@<NAS地址>:<NAS 备份根>/secrets/piggypal-secrets-*.tar.gz ~/

# 4. 解开
./scripts/backup-secrets.sh --restore ~/piggypal-secrets-20261030-120000.tar.gz --to /tmp/restore

# 5. 放回原位（权限 600）
cp /tmp/restore/server.env          server/.env
cp /tmp/restore/deploy.env          deploy.env
mkdir -p client/android ~/keys
cp /tmp/restore/android/key.properties client/android/key.properties
cp /tmp/restore/android/*.keystore  ~/keys/
chmod 600 server/.env deploy.env client/android/key.properties ~/keys/*.keystore

# 6. 核对 keystore 指纹（必须和 MANIFEST.txt 里一致）
keytool -list -v -keystore ~/keys/piggy-pal-debug.keystore -storepass android | grep SHA256

# 7. 验证真的能用
cd server && go test ./... && cd ..
./build.sh          # 能打出 APK 且签名校验通过，就算恢复成功
```

第 7 步能过，就说明**这个包真的能救你的命**；过不了，现在发现总比真出事时发现好。

## 5. 关于签名指纹

`release_apk.sh` 里有一段：

```sh
EXPECTED_SHA256="${PIGGYPAL_SIGN_SHA256:-a8ec22c1d255c0ae5436bbb41053038ee6743095f163a65353aca007f83bb56e}"
```

这是当前 App 的签名证书指纹，每次发版前都会校验——**对不上就不发**，避免手滑用错 keystore 造成「新版本装不上、老版本又升级不了」。

- 指纹是证书的公钥摘要，**不是秘密**（任何装了 App 的手机都能提取）
- 换签名（换 keystore）时同步改这个默认值，或用 `PIGGYPAL_SIGN_SHA256` 环境变量临时覆盖
- Fork 这个项目的人必须换成自己的，否则每次发版都会被拦下

## 6. 账号比文件更要紧

真要说「一锅端」，最可能的不是文件丢了，而是**账号进不去**：

| 账号 | 为什么关键 | 要做的 |
|---|---|---|
| 腾讯云 | 服务器、CAM 密钥、DNS 都挂在这一个号上 | 开 MFA，保存恢复码 |
| DNSPod / 域名商 | 域名一丢，所有客户端连不上 | 开 MFA，确认续费方式 |
| GitHub | 代码仓库（私有） | 开 MFA，保存恢复码 |
| 企业微信（告警群） | webhook 失效就收不到告警 | 至少两个人是群管理员 |

这些账号的密码和恢复码，**放进同一个密码管理器**（开 MFA 时它给的恢复码也要存）。

## 7. 什么时候该轮换

| 对象 | 触发条件 | 代价 |
|---|---|---|
| `API_TOKEN` | 怀疑泄露、设备丢失 | ⚠️ **要重发客户端**，所有设备升级 |
| CAM 密钥 | 泄露、人员变动 | 服务端换 `.env` 重启即可 |
| DeepSeek Key | 泄露、额度异常 | 同上 |
| Webhook | 群变更、泄露 | 群里重建机器人，改 `alert.env` |
| keystore | **基本不该换**，除非私钥泄露 | 所有设备卸载重装 |

## 8. 万一 keystore 真丢了

1. 生成新 keystore，改 `key.properties` 和 `release_apk.sh` 的指纹
2. 每台设备**卸载后重装**（覆盖安装会报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`）
3. 影响范围：
   - ✅ 孩子的学习数据在服务端，**不会丢**
   - ⚠️ 本机 `client_id` 会重置，服务端多出几条设备记录
   - ⚠️ 每台设备要重新选一次宝宝
4. 这也意味着：**这条路径能走，但很烦**。所以 keystore 要有三份。

纸只写「去哪儿找」：

```

备份包位置：<NAS 备份根>/secrets/piggypal-secrets-*.tar.gz
（包是明文，NAS 上这个目录只给管理员读）
密码管理器：<账号邮箱>（腾讯云 / DNS / GitHub 的恢复码）
keystore 指纹（SHA-256）：
  A8:EC:22:C1:D2:55:C0:AE:54:36:BB:B4:10:53:03:8E:E6:74:30:95:F1:63:A6:53:53:AC:A0:07:F8:3B:B5:6E
恢复步骤：docs/密钥与恢复.md 第 4 节
```

如果你担心「密码管理器本身也进不去」，就把密码管理器的**恢复码**（不是主密码）
另抄一张，和这张分开放在两个地方。
